## Context

当前 FastAPI 服务在每次生成请求中先运行 `kiro-cli chat --list-models`，再运行一次 `kiro-cli chat --no-interactive`。该方式复用了官方认证能力，但固定进程启动成本高、不能复用会话，而且所谓 SSE 只在 CLI 完成后发送一个正文块。企业账号还存在 IAM Identity Center 区域和 Kiro Profile/Runtime 区域不同的约束，直接读取认证数据库并拼接 Runtime 地址容易产生错误路由。

调用方包括 OpenCode、Claude Code、OpenAI SDK 和 Anthropic SDK。优化必须维持现有 JSON 接口、Bearer/x-api-key 鉴权、systemd 部署和官方 CLI 回退能力，同时避免将实验性直连变成单点故障。

## Goals / Non-Goals

**Goals:**

- 消除每请求模型查询和完整 CLI 冷启动造成的大部分固定延迟。
- 为 OpenAI Chat Completions、Responses 和 Anthropic Messages 提供真实增量流。
- 在多轮对话中复用 ACP 会话，并对并发、过期和异常恢复提供确定行为。
- 提供直接 Runtime、ACP 和一次性 CLI 的统一传输抽象与自动降级。
- 正确区分身份目录区域和推理区域，保护凭证并保持企业 SSO 可用。
- 建立性能、可靠性和降级行为的自动化验证与可观测性。

**Non-Goals:**

- 不绕过 Kiro 订阅、配额、模型权限或服务端策略。
- 不承诺将 Kiro 的所有工具语义无损转换为 OpenAI/Anthropic 工具协议。
- 不在第一阶段实现分布式多实例共享会话；单实例内存态为默认实现。
- 不将直接 Runtime 通道设为默认，除非兼容性、安全性和回归测试全部通过。

## Decisions

### 1. 建立统一异步传输接口

定义 `KiroTransport`，至少包含模型发现、开始生成、取消、健康检查和关闭方法。实现 `AcpTransport`、`CliTransport` 和实验性的 `RuntimeTransport`，上层路由与协议转换不感知具体传输。

默认顺序为 ACP → CLI；只有显式启用时才尝试 Runtime → ACP → CLI。选择结果和降级原因写入结构化日志与响应追踪信息。

替代方案是直接在路由中加入三套分支，但这会复制流式、取消、错误映射和会话逻辑，难以测试与回滚。

### 2. 模型发现采用 TTL + single-flight + stale-if-error

内存缓存保存模型快照、获取时间和来源。有效期内直接返回；过期时仅允许一个协程刷新，其他请求等待同一任务；刷新失败时，在最大陈旧窗口内返回最近成功快照并记录告警。认证变化、模型不存在错误和管理端刷新操作可主动失效缓存。

默认 TTL 为 300 秒，最大陈旧窗口为 3600 秒，均可配置。

### 3. ACP 使用有界常驻进程池

启动时创建最小数量 ACP 进程，按需扩展到上限。每个进程由独立的 JSON-RPC 读写循环管理，请求通过关联 ID 分发，stderr 单独记录。进程崩溃、协议损坏或超时后标记不健康，终止并补充新进程。

会话固定到某个 ACP worker；无会话请求按最少负载调度。优雅关闭时停止接收新请求、等待宽限期、取消剩余请求并关闭子进程。

相比单个全局 ACP 进程，进程池可以隔离长任务和崩溃；相比每请求进程，显著降低冷启动成本。

### 4. 会话映射采用显式 ID 优先和有界内存存储

按以下优先级获取外部会话 ID：标准/客户端会话头、请求体显式字段、服务端生成 ID。映射记录包含传输类型、worker、上游会话 ID、模型、创建时间、最后访问时间和当前锁。

同一会话内请求串行执行，避免上下文竞争；不同会话可并发。使用 TTL 与 LRU 双重限制清理，默认空闲 30 分钟、最多 1000 个会话。worker 失效时，会话可根据保存的规范化消息历史在新 worker 上恢复；恢复失败则创建新会话并返回可观测的重建标记。

### 5. 流式转换在传输事件层完成

传输层输出统一事件：文本增量、思考增量、工具事件、用量、结束和错误。协议适配器分别生成 OpenAI Chat、OpenAI Responses 和 Anthropic Messages 的标准事件序列。

响应头发送后发生错误时使用协议内错误事件；响应头发送前发生错误时使用普通 HTTP 错误。客户端断开必须向传输传播取消，释放 worker 和会话锁。

为避免 Unicode 破损，按解码器边界处理字节，禁止任意切割多字节字符。

### 6. Runtime 区域从 Kiro Profile 推导

Identity Center 区域仅用于 OIDC/SSO 令牌交换；Runtime 区域从 profile ARN、官方 CLI 暴露的 profile 元数据或已验证的管理接口获得。二者分别存储，禁止以身份区域构造 Runtime 地址。

Runtime 通道使用短期访问令牌、最小化内存驻留并在日志中彻底脱敏。遇到 401/403 先执行一次受控刷新；遇到协议不兼容、区域不可达或连续 5xx 时熔断并降级 ACP。

### 7. 分阶段交付与性能门槛

按缓存、增量流、ACP、会话、Runtime 的顺序启用，每项由独立配置开关控制。基准测试记录冷启动、热请求、首字时间、总时长、并发吞吐和进程数。

目标是在本机热请求中将代理固定开销降至 500 毫秒以内，将首个文本事件在上游首个文本事件后 100 毫秒内转发。性能门槛不包含模型自身推理时间。

## Risks / Trade-offs

- [ACP 协议或 CLI 版本变化] → 启动时协商能力、固定兼容测试矩阵，并保留一次性 CLI 回退。
- [直接 Runtime 使用非稳定协议] → 默认关闭、显式开关、熔断降级，不将其作为完成其他优化的前置条件。
- [会话复用导致串话] → 强制租户/API Key 与外部会话 ID 共同命名空间化，同会话加锁，增加隔离测试。
- [缓存返回过期模型] → 设置最大陈旧窗口，模型不存在时主动失效并重试一次。
- [真正流式改变客户端观察到的时序] → 遵循标准事件格式，提供短期兼容开关并在发布说明中标注。
- [客户端断开后子进程继续消耗 credits] → 传播取消、设置终止宽限期并监控孤儿任务。
- [工具输出或日志泄露凭证] → stdout/stderr 分离、字段级脱敏、禁止记录 Authorization、token 和完整认证数据库内容。
- [常驻进程提高基础内存] → 池大小可配置、空闲回收，并以延迟收益和内存上限共同验收。

## Migration Plan

1. 引入模块边界、配置与指标，但继续使用 `CliTransport`，建立行为基线。
2. 启用模型缓存，验证认证变化和模型刷新。
3. 实现统一事件与真实 SSE，通过兼容开关逐步启用。
4. 上线 ACP 单 worker，再扩展为进程池；异常时自动回退 CLI。
5. 启用会话映射和恢复，先限制在显式 session ID 的请求。
6. 实现实验性 Runtime 通道，仅在测试环境和白名单账号启用。
7. 性能与稳定性达标后将 ACP 设为默认，保留 CLI 回滚开关。

回滚时按相反顺序关闭 Runtime、会话复用、ACP 和增量流；模型缓存可独立禁用。所有阶段均不改变现有 API Key 和 systemd 服务入口。

## Open Questions

- Kiro CLI 2.14 的 ACP 是否暴露稳定的模型切换、会话恢复和取消能力，哪些能力需要代理侧补偿？
- OpenAI/Anthropic 客户端会话 ID 的最终优先级和响应回传头是否需要提供可配置策略？
- Runtime 通道的官方支持边界和服务条款是否允许长期作为本地代理传输？
- 会话历史是否仅保存在内存，还是需要可选的加密本地持久化以支持服务重启恢复？
